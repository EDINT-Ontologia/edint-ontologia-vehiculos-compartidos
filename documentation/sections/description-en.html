Ontology for the representation of data on shared vehicle systems: Description back to index

Figure 1 shows the classes and properties of the shared vehicle systems ontology. The main objective of this portion of the ontology is to allow the representation of the routes taken by the vehicles in a system.

To represent a route, we have the concept of Route which must have an associated Shared Vehicle and, in turn, both an origin dock and a destination dock if the system model is station-based. If the model is "Free", then the route will have both an origin parking spaceand a destination parking space. A route can have a series of waypoints. Additionally, this ontology uses several SKOS concept schemas to represent a vehicle's state (active, under repair, abandoned), its propulsion type (electric, gasoline, etc.), and its vehicle type (car, bicycle, scooter, etc.). To represent the possible waypoints of the routes, expressed in terms of their longitude and latitude, the classes ggeosparql:Feature, geosparql:SpatialObject, geosparql:Geometry y geosparql:Point have been reused from the geosparql vocabulary, following the "Location Pattern" in Figure 1.

Furthermore, all observations regarding the availability of station docks are represented, as shown in Figure 2. The design pattern from the Semantic Sensor Network Ontology is reused.

The main concept is Dock for which the classes sosa:Sensor, sosa:Observation, sosa:ObservableProperty, sosa:Platform and sosa:FeatureOfInterest are reused, of the sosa ontology. Specifically, we will observe the availability of a dock, which is the property to be observed, and for which the result of the observation will be obtained. This property allows you to represent the number of empty (free) docks, and the number of occupied docks, which are also observable properties of the Station in general.

3.1 Usage Examplesback to índice

To represent a shared vehicle station, an instance of the class edintvehcom:SharedVehicleStation is created with the properties dct:identifier, schema:name (station name), schema:address (station address), and edintvehcom:comissioningDate (commissioning date). The station is also linked, via the edintvehcom:stationState property, to the corresponding SKOS concept in the station state schema, which in this example is an operational station. with the organization that operates it through edintvehcom:operatedBy, and with its docks through edintvehcom:hasDock.
Next, two instances of edintvehcom:Dock are represented. For each dock, its identifier is indicated by dct:identifier and its state by the property edintvehcom:dockState, which links to the corresponding SKOS concept in the dock state schema. In the example, the docks are in the active state.
To represent a shared vehicle, an instance of the class edintvehcom:SharedVehicle is created. In the example, its identifier is specified, its vehicle type using edintveh:vehicleType, its propulsion system type using edintvehcom:propulsionSystemType, its state using edintvehcom:vehicleState, and its manufacturer using schema:manufacturer. The properties `edintvehcom:propulsionSystemType` and `edintvehcom:vehicleState` link to the corresponding SKOS concepts; in this case, an electric bicycle in its active state is represented.
span class="markdown"> To represent a route of a station-based system, an instance of the class edintvehcom:Route is created with the properties dct:identifier, schema:startDate and schema:endDate. The route is linked to the vehicle using edintvehcom:madeByVehicle, to the origin dock using edintvehcom:originDock, to the destination dock using edintvehcom:destinationDock, and to its waypoints using edintvehcom:hasWaypoint. Each waypoint is represented as an instance of edintvehcom:Waypoint, with its order, date and time of passage, and associated geometry.
In the case of a free model, the route does not necessarily begin or end at a station's dock points. Therefore, the instance of edintvehcom:Route is related to an origin parking space by edintvehcom:originSpot and to a destination parking space by edintvehcom:destinationSpot. Parking spaces are represented as instances of edintapar:ParkingSpot.
To represent an observation about the availability of an dock, an instance of edintvehcom:DockSensor is created, hosted on the station by sosa:isHostedBy, and which observes the property edintvehcom:dockAvailability. The observation is represented with an instance of edintvehcom:DockObservation, indicating the observed dock using sosa:hasFeatureOfInterest, the sensor performing the observation using sosa:madeBySensor, the observed property using sosa:observedProperty, the observation time using sosa:phenomenonTime, and the result using sosa:hasResult with an instance of qudt:QuantityValue.
Finally, an aggregated observation about the station is displayed to indicate the number of empty docks. In this case, the feature of interest is the vehicle-sharing station itself, and the observed property is edintvehcom:numberEmptyDocks. The result is also expressed using sosa:hasResult and qudt:QuantityValue.
